# Регламент загрузки данных в БД

Документ фиксирует полный порядок загрузки данных из файлов учёта в БД `ias_vniic` (схема `tech_accounting`).

Регламент обязателен для чистовой загрузки после очистки БД и для повторных прогонов импорта из **«Основной Учет.xlsx»**.

При расхождении с `docs/import_ou/РЕГЛАМЕНТ_ПАРСИНГА.md` по правилам разбора столбцов приоритет у регламента парсинга; настоящий документ определяет **операционный порядок** загрузки и контроль в БД.

---

## 1. Обязательный комплект документов

Перед загрузкой должны быть актуальны следующие документы:

| № | Документ | Назначение |
|---|----------|------------|
| 1 | `docs/import_ou/РЕГЛАМЕНТ_ПАРСИНГА.md` | Правила парсинга столбцов, неатомарных значений, синтетических номеров, листов АРМ и Принтеры. |
| 2 | `docs/bd/МАППИНГ_КОЛОНОК_УЧЕТ_ТС.md` | Соответствие колонок «Учёт ТС» и полей БД (в т.ч. тип части «Накопитель» для столбца «Диск»). |
| 3 | `docs/bd/СТРУКТУРА_ЛИСТА_АРМ_ОСНОВНОЙ_УЧЕТ.md` | Структура листов источника. |
| 4 | `docs/sistema/УТОЧНЕНИЕ_УЧЕТ_МОНИТОРЫ_ИБП_МЦ04.md` | Принцип «одна запись equipment = один физический актив»; учёт мониторов и ИБП. |
| 5 | `scripts/create_ias_vniic.sql` | Эталон DDL при развёртывании БД без Yii-миграций. |
| 6 | `docs/bd/СРАВНЕНИЕ_БД_ДАМП_И_РАБОЧАЯ.md` | Отличия схемы дампа и рабочей БД после миграций приложения. |

## 2. Каналы импорта

В проекте используются **разные** контуры; для наполнения из «Основной Учет.xlsx» применяется только один из них.

| Канал | Назначение | Источник | Протокол | Использовать для OУ |
|-------|------------|----------|----------|---------------------|
| **`scripts/load_ou_main.py`** | Чистовая/повторная загрузка листов **АРМ** и **Принтеры** | `Основной Учет.xlsx` | stdout (обязательно сохранить); запись в `import_runs` — целевое состояние, пока не реализована в скрипте | **Да** |
| **`scripts/load_ou_test_20rows.py`** | Тест на 20 строках листа АРМ | `ОУ_тест.xlsx` | stdout | Только проверка парсинга |
| **`ImportController`** (`/import`) | Упрощённый импорт листа АРМ | Произвольный xlsx | Сообщения в ответе страницы | **Нет** (не покрывает регламент парсинга) |
| **`ArmController`** (`import-preview` / `import-apply`) | Ручная дозагрузка по шаблону с ID справочников | Шаблон `equipment_import_template.xlsx` | `equipment_import_logs` | **Нет** (не парсит «Основной учёт») |

**Итог:** первичное наполнение и перезагрузка данных предприятия выполняются скриптом `load_ou_main.py`. Web-импорт в «Учёт ТС» — для точечного обновления по шаблону, не заменяет регламент OУ.

## 3. Источники загрузки

### 3.1. Приоритетные листы

- `Основной Учет.xlsx` → лист **АРМ** (ПК, ноутбуки, моноблоки, мониторы, ИБП).
- `Основной Учет.xlsx` → лист **Принтеры** (`Принтер` / `МФУ`).
- **`ОУ.xlsx`** (укороченный выгрузочный файл того же формата листа «АРМ», как правило 18–23 столбца) — допустимый источник для `scripts/load_ou_main.py` через `OU_MAIN_EXCEL`; правила парсинга и связки **те же**, что для полного файла.

### 3.2. Листы второго контура

- `Поставки 2017-2019` … `Поставки 2025` — обогащение поставщиком и датами (отдельный этап).
- `СБ забрали`, `Принтеры забрали`, `Мониторы забрали` — только архивный этап, не смешивать с активным учётом.

## 4. Подготовка среды и предзагрузочная проверка

### 4.1. Развёртывание БД

**Вариант А — среда приложения (рекомендуется):**

1. Создать БД `ias_vniic`.
2. Применить миграции Yii2 из каталога `ias_uch_vnii/migrations/` (в т.ч. `equipment_types`, `equipment_links`, `equipment_import_logs`).
3. Убедиться в наличии учётной записи администратора и роли `admin`.

**Вариант Б — только SQL-эталон:**

1. Выполнить `scripts/create_ias_vniic.sql`.
2. Учесть: в эталоне тип техники — столбец `equipment.equipment_type` (varchar); в рабочей среде после миграций — справочник `equipment_types` и поле `equipment_type_id` (см. `docs/bd/СРАВНЕНИЕ_БД_ДАМП_И_РАБОЧАЯ.md`).

### 4.2. Чистовая загрузка (очистка операционных данных)

Перед чистовым прогоном удалить операционные данные с сохранением справочников и администратора:

```bash
cd ias_uch_vnii
php yii purge/keep-admin --force=1
```

Альтернатива: полное пересоздание БД по `create_ias_vniic.sql` с последующим `php yii migrate`.

### 4.3. Проверки перед запуском импорта

1. БД доступна: `ias_vniic`, схема `tech_accounting`.
2. Справочники и статусы: `dic_equipment_status` (в т.ч. `in_use`), `spr_parts`, `spr_chars`, при схеме приложения — `equipment_types`, `roles`.
3. Таблицы контура учёта: `equipment`, `users`, `locations`, `part_char_values`, `equipment_links` (для связей ПК → монитор/ИБП в UI).
4. Уникальность `equipment.inventory_number`; уникальность `(equipment_id, part_id, char_id)` в `part_char_values`.
5. Файл источника:
   - по умолчанию `Основной Учет.xlsx` в корне проекта;
   - либо переменная окружения `OU_MAIN_EXCEL`.
6. Параметры подключения к PostgreSQL (при необходимости): `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` (значения по умолчанию — в начале `scripts/load_ou_main.py`).
7. Зависимости Python: `pip install openpyxl psycopg2-binary`.

## 5. Порядок загрузки в БД

Логический порядок (соответствует `РЕГЛАМЕНТ_ПАРСИНГА.md`, п. 1.3):

| Шаг | Действие | Таблицы |
|-----|----------|---------|
| 1 | Справочники статусов, частей, характеристик; при схеме приложения — типы техники | `dic_equipment_status`, `spr_parts`, `spr_chars`, `equipment_types` |
| 2 | Пользователи из колонки «Пользователь» | `users`, `user_roles` |
| 3 | Помещения из колонки «Помещение» | `locations` |
| 4 | Основные активы листа **АРМ** (СБ, ноутбук, моноблок; строка «только монитор») | `equipment` |
| 5 | Дочерние активы листа **АРМ** (отдельные записи на каждый монитор и ИБП) | `equipment` |
| 6 | Активы листа **Принтеры** | `equipment` |
| 7 | **Связи комплекта** (обязательно, см. п. 5.1) | `equipment_links` (`link_type`: `monitor`, `ups`) |
| 8 | Характеристики (ЦП, ОЗУ, накопитель, ОС, IP, имя ПК, антивирус, исходные учётные признаки) | `part_char_values` |
| 9 | История создания (при принятом сценарии) | `equip_history` |
| 10 | Протокол импорта | `import_runs` / `import_errors` и/или `equipment_import_logs` |

**Примечание по шагам 7–8:** в интерфейсе «Учёт ТС» колонка «Монитор», счётчики «Мониторы (шт)» / «ИБП (шт)» и сценарий «Переместить компонент» опираются на `equipment_links`. Отдельные записи `equipment` без связи родительского ПК с дочерними мониторами и ИБП **не образуют комплект** и **не считаются завершённой загрузкой**.

### 5.1. Обязательная связка системного блока с мониторами и ИБП

#### 5.1.1. Понятие комплекта

**Одна строка листа «АРМ»** в источнике (при наличии системного блока / ноутбука / моноблока) соответствует **одному рабочему комплекту** (АРМ пользователя):

| Роль в комплекте | Источник в Excel | Запись в `equipment` | Связь в `equipment_links` |
|------------------|------------------|----------------------|---------------------------|
| Родитель (хост) | «Системный блок», «№ системн. блока» | Тип: `Системный блок`, `Ноутбук` или `Моноблок` | — |
| Дочерний актив | «Монитор» (каждая модель — отдельная запись) | Тип: `Монитор`, инв. № `МЦ.04-mon-XXX` | `link_type = monitor` |
| Дочерний актив | «Другая техника» (подстроки «ИБП …») | Тип: `ИБП`, инв. № `МЦ.04-ups-XXX` | `link_type = ups` |

Строка «только монитор» (без системного блока) загружается **одной** записью `equipment` без родительской связи.

#### 5.1.2. Обязательные правила связки

1. После создания записей шагов 4–5 для строки-ПК **должны** быть созданы связи:
   - `parent_equipment_id` — идентификатор хоста (системный блок / ноутбук / моноблок) **этой же строки**;
   - `child_equipment_id` — идентификатор монитора или ИБП, созданного **из той же строки**;
   - `link_type` — `monitor` или `ups` соответственно.
2. **Несколько мониторов в одной строке** (ячейка «Монитор»: перенос строки `\n` или разделитель `;` / `; `) → **на каждый** физический монитор:
   - отдельная запись `equipment` (тип «Монитор», инв. № `МЦ.04-mon-XXX`);
   - **отдельная** связь `equipment_links` с `link_type = monitor` к **одному** родительскому системному блоку этой строки.
3. Несколько ИБП в «Другая техника» → несколько записей `equipment` и несколько связей `ups` с тем же родителем.
4. Дубликаты связей запрещены: уникальность `(parent_equipment_id, child_equipment_id, link_type)`.
5. **Загрузка без шага 7 недопустима** для эксплуатации раздела «Учёт ТС»: техника отображается разрозненно, комплект не восстанавливается автоматически по ответственному пользователю.

#### 5.1.3. Пример комплекта (одна строка Excel)

| Пользователь | Системный блок | Монитор | Другая техника |
|--------------|----------------|---------|----------------|
| Иванова И.И. | UNIVERSAL D1 | MSI PRO MP271AP<br>Samsung S22C200 | ИБП Powercom … |

**Ожидаемый результат в БД:**

| Записи `equipment` | Связи `equipment_links` |
|--------------------|-------------------------|
| 1 × системный блок (родитель) | — |
| 2 × монитор (дочерние) | 2 × `monitor` → один и тот же `parent_equipment_id` |
| 1 × ИБП (дочерний) | 1 × `ups` → тот же родитель |

**Итого:** 4 записи `equipment`, 3 связи. Счётчик «Мониторы (шт)» у ПК в «Учёт ТС» = 2.

#### 5.1.4. Алгоритм сопоставления при импорте

Сопоставление выполняется **в пределах одной строки Excel** (те же синтетические инвентарные номера, что при создании `equipment`):

1. Определить `inventory_number` родителя (столбец «№ системн. блока», с учётом суффикса `-строкаN` при коллизиях).
2. Определить число **физических** мониторов комплекта функцией `monitor_kit_entries` (см. п. 5.1.6) — **только** по столбцу «Монитор» и, при нескольких **реальных** «№ монитора» в одной ячейке; **для каждой** модели — дочерняя запись `МЦ.04-mon-…` и связь `monitor` с родителем.
3. Для каждой подстроки «ИБП …» из «Другая техника» — дочерняя запись `МЦ.04-ups-…` и связь `ups`.

#### 5.1.5. Число мониторов в комплекте (критично для «Учёт ТС»)

**Источник количества записей `equipment` типа «Монитор» и связей `equipment_links` (`link_type = monitor`):**

| Учитывается | Не учитывается как второй/дополнительный монитор |
|-------------|--------------------------------------------------|
| Столбец **«Монитор»**: каждая подстрока после `monitor_parts` (`\n`, `; `) | Столбец **«№ монитора»** сам по себе (в т.ч. `НИИСУ`, `МЦ.04`) — только `part_char_values` у строки-ПК |
| Несколько **реальных** (не повторяющихся) номеров в **одной** ячейке «№ монитора» через `\n` при **одной** модели в «Монитор» — столько же активов-мониторов с той же моделью | Столбцы **19–21** («… в ведомости бух. инвентаризации МЦ»): справочные пометки бухучёта, **не** создают отдельный `equipment` и **не** увеличивают счётчик «Мониторы (шт)» |

**Пример (один физический монитор, файл `ОУ.xlsx`):**

| Пользователь | Монитор | № монитора | Монитор в ведомости бух. (кол. 20) |
|--------------|---------|------------|-------------------------------------|
| Аптекарева В. М. | Nec MultiSync E222W | НИИСУ | МЦ.04.1 |

**Ожидаемо в БД:** 1 запись `equipment` («Монитор») + 1 связь `monitor` к ПК. Значение `МЦ.04.1` в колонке ведомости **не** трактуется как второй монитор при одной модели в столбце «Монитор».

**Пример (два физических монитора):**

| Монитор |
|---------|
| AOC 24P2Q<br>AOC 24P2Q |

**Ожидаемо:** 2 записи «Монитор» + 2 связи `monitor`.

Реализация в `scripts/load_ou_main.py`: `monitor_kit_entries()`; контроль после прогона — строка «Контроль: мониторов в источнике … / создано …» в stdout.

#### 5.1.6. Реализация в скриптах

| Средство | Шаг 7 |
|----------|-------|
| `scripts/load_ou_main.py` | **Обязателен:** создаёт `equipment` на мониторы по `monitor_kit_entries`, `equipment_links` при импорте; в конце прогона досоздаёт связи (`link_arm_kits_existing`) по тому же файлу. |
| `scripts/link_ou_kits_only.py` | Восстановление комплектов: связи + досоздание отсутствующих мониторов/ИБП по строкам файла (та же логика `monitor_kit_entries`). |
| Web «Учёт ТС» → «Переместить компонент» | Ручная доработка отдельных комплектов; **не заменяет** массовую загрузку OУ. |

**Прочие ограничения `load_ou_main.py`:**

- выполняет шаги 1–8 (характеристики — вместе с шагами 4–5; связи — шаг 7, п. 5.1);
- **не выполняет** шаг 10 (запись в таблицы протокола БД);
- не заполняет `equip_history` (шаг 9);
- при схеме с `equipment_type_id` может записывать тип в `equipment.equipment_type` (varchar); при необходимости синхронизировать справочник `equipment_types` отдельно.

## 6. Правила качества данных

### 6.1. Уникальность инвентарных номеров

Повторяющиеся учётные признаки (`МЦ.04`, `НИИСУ`, `Электроника`, `99036` и подобные) не загружать как единый `equipment.inventory_number` для разных активов.

Использовать внутренние номера:

- `МЦ.04-pc-XXX`
- `МЦ.04-mon-XXX`
- `МЦ.04-ups-XXX`
- `МЦ.04-prn-XXX`

Исходное значение сохранять в `description` или `part_char_values`.

### 6.2. Неатомарные значения

- Базовый разделитель: `\n`.
- Для столбца **Диск** в полном файле — также запятая.
- Для **Монитор** — допускается `; `.
- Столбцы **19–21** (ведомость бух. инвентаризации МЦ): при загрузке в `equipment` **не** используются; при необходимости учёта — только в `description` / `part_char_values` по отдельному решению (см. `РЕГЛАМЕНТ_ПАРСИНГА.md`, п. 3).

### 6.3. Ограничение `part_char_values`

До изменения схемы множественные значения одного типа характеристики для одного актива хранить в одной записи `value_text` (разделитель — перенос строки или `; `), если нарушается уникальность `(equipment_id, part_id, char_id)`.

Столбец Excel «Диск» → тип части **«Накопитель»**, характеристика **«Модель»** (см. маппинг).

### 6.4. Типы техники

| Схема БД | Поле | Значения |
|----------|------|----------|
| После `create_ias_vniic.sql` | `equipment.equipment_type` | Текст: `Системный блок`, `Ноутбук`, `Моноблок`, `Монитор`, `ИБП`, `Принтер`, `МФУ` |
| После миграции `equipment_types` | `equipment.equipment_type_id` | Ссылка на справочник; наименования — те же |

## 7. Минимальный контроль после загрузки

1. Количество активов по типам: ПК/ноутбук/моноблок, монитор, ИБП, принтер/МФУ.
2. Отсутствие дубликатов `equipment.inventory_number`.
3. Ссылочная целостность: `responsible_user_id`, `location_id` — без «висячих» ID.
4. **Связи и полнота комплекта:**
   - для каждой строки-ПК число связей `monitor` **равно** числу элементов `monitor_kit_entries` (не столбцам ведомости 19–21);
   - в stdout: «мониторов в источнике» = «создано записей мониторов при импорте»;
   - число связей `ups` **равно** числу подстрок «ИБП …» в «Другая техника»;
   - нет «осиротевших» мониторов без `parent_equipment_id` (кроме строк «только монитор»).
5. Характеристики в `part_char_values`: ЦП, ОЗУ, накопитель (диск), ОС, IP, имя ПК, антивирус — по выборке строк.
6. Повторяющиеся учётные признаки не вызвали конфликта уникальности; исходные значения сохранены в описании/характеристиках.
7. Протокол: сохранённый stdout CLI и/или запись в `equipment_import_logs` / `import_runs`.
8. В web-приложении: грид «Учёт ТС» отображает данные; у ПК корректны счётчики связанных мониторов/ИБП (после выполнения шага 7).

**Примеры контрольных запросов:**

```sql
-- Дубликаты инвентарных номеров
SELECT inventory_number, COUNT(*) FROM equipment
GROUP BY inventory_number HAVING COUNT(*) > 1;

-- Мониторы без связи с родительским ПК (после чистовой загрузки ожидается 0)
SELECT e.id, e.inventory_number FROM equipment e
WHERE COALESCE(e.equipment_type, '') = 'Монитор'
  AND NOT EXISTS (
    SELECT 1 FROM equipment_links el
    WHERE el.child_equipment_id = e.id AND el.link_type = 'monitor'
  );

-- ПК, у которых связей monitor меньше, чем должно быть (выборочно сверить с Excel)
-- Ожидается 0 строк после корректного импорта
SELECT p.inventory_number, p.name,
       COUNT(el.id) FILTER (WHERE el.link_type = 'monitor') AS mon_links
FROM equipment p
LEFT JOIN equipment_links el ON el.parent_equipment_id = p.id
WHERE COALESCE(p.equipment_type, '') IN ('Системный блок', 'Ноутбук', 'Моноблок')
GROUP BY p.id, p.inventory_number, p.name;
```

## 8. Команды запуска

### 8.1. Подготовка (среда приложения)

```bash
cd ias_uch_vnii
php yii migrate
php yii purge/keep-admin --force=1
```

### 8.2. Основная загрузка из «Основной Учет»

```bash
# из корня репозитория

```

В stdout должны быть строки о числе созданных связей ПК → монитор/ИБП. Отсутствие связей при ненулевом числе мониторов/ИБП — **блокирующий дефект** загрузки.

## 9. Критерии готовности к эксплуатации

Загрузка считается корректной, если:

1. Выполнен порядок раздела 5, **обязательно включая шаг 7** (связи `equipment_links`, п. 5.1) для всех строк-ПК с мониторами и/или ИБП в источнике.
2. Выполнены проверки раздела 7.
3. Нет блокирующих ошибок в протоколе импорта.
4. Маппинг соответствует `РЕГЛАМЕНТ_ПАРСИНГА.md`.
5. Результат подтверждён ответственным за данные.

**Допущение:** карточки пользователей (`user_equipment_cards`) при CLI-загрузке не создаются автоматически; при необходимости инициализируются при первом обращении к контуру карточек или отдельной процедурой.
