# План доработок: учет ТС и карточки пользователя

## 1. Цель документа

Документ фиксирует перечень доработок по учету технических средств (ТС), их структурирование в виде задач и подзадач, а также поэтапный план реализации.

## 2. Область изменений

В рамках доработки затрагиваются:
- учет и связи ТС (системный блок, монитор, ИБП, принтер, МФУ, сканер, диски и др.);
- операции переназначения и перемещения ТС;
- пользовательский интерфейс (модальные формы, таблица учета, фильтры, колонки);
- карточки ответственности пользователя за закрепленную технику;
- экспорт/импорт данных (DOCX, XLSX) с валидацией;
- контроль статусов техники и выборки по статусам.

## 3. Основные бизнес-правила (переформулировано)

### 3.1 Привязка техники
1. Система должна обеспечивать привязку мониторов и ИБП к системному блоку.
2. Система должна обеспечивать привязку принтеров, МФУ и сканеров к пользователю и кабинету.
3. Система должна поддерживать отображение нескольких мониторов у одного системного блока.
4. Система должна поддерживать отображение нескольких дисков у одного системного блока.

### 3.2 Перепривязка и перемещение
1. Система должна обеспечивать перепривязку всей техники пользователя целиком другому пользователю.
2. Система должна обеспечивать частичную перепривязку отдельных единиц техники (например, один монитор на другой системный блок).
3. Система должна обеспечивать выбор помещения при массовом переносе техники.
4. Система должна обеспечивать сценарий увольнения пользователя:
   - передача техники другим пользователям;
   - либо перевод всей техники на склад.

### 3.3 Карточки техники пользователя
1. Система должна формировать карточку пользователя с перечнем всей закрепленной за ним техники.
2. Система должна обеспечивать скачивание карточки пользователя в формате DOCX.
3. Система должна вести реестр карточек с ручным подтверждением администратором факта бумажного подписания.
4. Система должна автоматически снимать признак подписания карточки при:
   - изменении местоположения техники;
   - изменении закрепления техники за пользователем.
5. Система должна иметь раздел карточек с вкладками:
   - «Все карточки»;
   - «Неподписанные карточки».
6. При отсутствии закрепленной техники карточка пользователя не создается и не требуется.

### 3.4 Статусы и визуализация
1. Система должна иметь статус у каждой единицы техники.
2. Система должна отображать визуальные индикаторы статуса рядом с наименованием:
   - зеленый индикатор — «В эксплуатации»;
   - желтый индикатор — «В ремонте»;
   - красный индикатор — «На списание».
3. Система должна обеспечивать фильтрацию и выборки по статусам (например, вся техника «В ремонте» или «На списание»).

### 3.5 Таблица учета и обмен данными
1. В учете ТС должен быть выбор отображаемых столбцов.
2. Система должна обеспечивать экспорт таблицы учета в XLSX.
3. Система должна предоставлять шаблон XLSX для пакетного добавления новой техники.
4. Система должна обеспечивать импорт XLSX с валидацией данных и подтверждением администратора перед окончательной загрузкой.

## 4. Декомпозиция: задачи и подзадачи

### 4.1 Задача A. Модель данных и связи техники
Подзадачи:
1. Спроектировать связи:
   - `системный блок -> мониторы (1:N)`;
   - `системный блок -> диски (1:N)`;
   - `системный блок -> ИБП (0..N или 0..1 по итогам уточнения)`;
   - `пользователь/кабинет -> принтер/МФУ/сканер`.
2. Определить ограничения целостности и правила каскадного обновления.
3. Подготовить и применить миграции БД.
4. Добавить индексы для ускорения фильтрации по статусам, пользователю, кабинету, связям комплектующих.

Критерии готовности:
- связи корректно сохраняются и читаются;
- отсутствуют «висячие» ссылки;
- запросы списка техники работают в приемлемое время.

### 4.2 Задача B. Перенос/переназначение техники
Подзадачи:
1. Реализовать сервисный слой операций переназначения:
   - массовый перенос всего комплекта пользователя;
   - частичный перенос выбранных единиц;
   - перенос компонента между системными блоками;
   - перенос на склад.
2. Реализовать бизнес-правило «увольнение пользователя» с мастером действий.
3. Добавить журналирование операций переноса/перепривязки (кто, когда, что изменил).
4. Добавить транзакционный режим на массовые операции (atomic update).

Критерии готовности:
- сценарии переноса выполняются без потери связей;
- операции логируются;
- при ошибке выполняется откат транзакции.

### 4.3 Задача C. Модальное окно «Перенести/Переназначить»
Подзадачи:
1. Спроектировать UX-форму с режимами:
   - «Перенести комплект целиком»;
   - «Перенести выбранные единицы»;
   - «Переместить компонент на другой системный блок»;
   - «Передать на склад».
2. Добавить зависимые поля формы:
   - выбор целевого пользователя;
   - выбор целевого помещения;
   - выбор целевого системного блока (для монитора/диска/ИБП).
3. Добавить предварительный просмотр изменений до подтверждения.
4. Добавить валидацию на UI и сервере.

Критерии готовности:
- все ключевые сценарии выполняются из одного модального окна;
- пользователю понятен результат до подтверждения;
- некорректные комбинации блокируются валидацией.

### 4.4 Задача D. Отображение нескольких мониторов/дисков у системного блока
Подзадачи:
1. Определить формат представления (вложенный список, раскрывающиеся строки, отдельная вкладка деталей).
2. Добавить отображение агрегированной информации в таблице (например, количество мониторов/дисков).
3. Реализовать детальное представление по клику.
4. Добавить быстрые действия «отвязать/переместить» для каждой единицы.

Критерии готовности:
- у системного блока корректно показываются все привязанные мониторы и диски;
- переход к действиям по компонентам доступен без лишней навигации.

### 4.5 Задача E. Карточки пользователя и подтверждение подписи
Подзадачи:
1. Создать сущность карточки и состояние подписания (`подписана/не подписана`).
2. Реализовать генерацию DOCX по пользователю.
3. Реализовать реестр карточек с вкладками:
   - все карточки;
   - неподписанные карточки.
4. Реализовать ручное подтверждение подписания администратором.
5. Реализовать автоматический сброс признака «подписана» при изменениях состава/локации техники.
6. Добавить правило: при отсутствии техники карточка не создается.

Критерии готовности:
- карточка формируется и скачивается в DOCX;
- подпись отслеживается корректно;
- при изменениях автоматически появляется карточка в списке неподписанных.

### 4.6 Задача F. Статусы техники и списки по статусам
Подзадачи:
1. Уточнить и зафиксировать единый справочник статусов.
2. Добавить визуальные индикаторы статусов в таблицах и карточках.
3. Реализовать преднастроенные фильтры/представления:
   - «В ремонте»;
   - «На списание»;
   - «В эксплуатации».
4. Добавить отдельный раздел или сохраненные представления по статусам (по итогам UX-решения).

Критерии готовности:
- статус присутствует у всех единиц техники;
- визуальные индикаторы единообразны;
- выборки по статусам доступны в 1-2 действия.

### 4.7 Задача G. Настройка столбцов и XLSX экспорт/импорт
Подзадачи:
1. Расширить выбор отображаемых столбцов в таблице учета.
2. Реализовать экспорт текущего представления таблицы в XLSX.
3. Подготовить шаблон XLSX для массового добавления техники.
4. Реализовать пошаговый импорт:
   - загрузка файла;
   - валидация;
   - протокол ошибок;
   - предварительный просмотр;
   - подтверждение администратором;
   - загрузка в БД.
5. Добавить журнал импортов (кто, когда, сколько строк, сколько ошибок).

Критерии готовности:
- экспорт формируется корректно;
- импорт блокирует некорректные данные;
- администратор подтверждает итог до записи в БД.

## 5. Поэтапный план реализации

### Этап 1. Базовая архитектура и данные
- Задачи: A, F(частично).
- Результат: готовая модель связей, статусы и индексы, база для UI-операций.

### Этап 2. Операции переназначения
- Задачи: B, C.
- Результат: рабочие сценарии массового/частичного переноса и сценарий увольнения.

### Этап 3. Представление комплектов и компонентов
- Задачи: D.
- Результат: корректная визуализация нескольких мониторов/дисков и действия по компонентам.

### Этап 4. Карточки пользователя
- Задачи: E.
- Результат: DOCX-карточки, контроль подписания, вкладки реестра карточек.

### Этап 5. Обмен данными и финальный UX
- Задачи: G, F(завершение).
- Результат: выбор столбцов, XLSX экспорт/импорт, фильтры и представления по статусам.

### Этап 6. Тестирование и ввод в эксплуатацию
- Функциональное тестирование по сценариям переноса, увольнения, карточек и импорта.
- Нагрузочная проверка списка ТС и фильтров.
- Подготовка пользовательской инструкции для администраторов.

## 6. Приоритеты (MVP)

### Высокий приоритет (в первую очередь)
1. Связи техники и корректная модель данных (A).
2. Перепривязка/перенос, включая увольнение (B, C).
3. Статусы техники и фильтрация по статусам (F).

### Средний приоритет
1. Отображение нескольких мониторов/дисков (D).
2. Карточка пользователя DOCX + контроль подписания (E).

### Нормальный приоритет
1. XLSX экспорт/импорт с подтверждением (G).
2. Дополнительные UX-улучшения таблиц.

## 7. Риски и открытые вопросы

1. Требуется подтвердить точную кардинальность связи ИБП с системным блоком (0..1 или 0..N).
2. Требуется согласовать формат отображения многокомпонентных связей в таблице (плоско/вложенно/детальная панель).
3. Требуется согласовать макет бумажной карточки для DOCX (поля, подписи, реквизиты).
4. Требуется согласовать обязательные поля XLSX-шаблона и правила валидации.

## 8. Критерии приемки доработок (верхнеуровнево)

1. Все описанные сценарии привязки и перепривязки доступны и отрабатывают без нарушения целостности данных.
2. Карточки пользователя формируются, скачиваются и корректно управляются по статусу подписания.
3. Статусы техники визуально понятны и позволяют быстро получать выборки.
4. Экспорт/импорт XLSX работают с валидацией и подтверждением администратора.
5. Выбор отображаемых столбцов доступен в учете ТС и сохраняет работоспособность таблицы.

## 9. Бэклог на спринты

Принятые допущения для планирования:
- 1 спринт = 2 недели;
- команда: 1 backend + 1 frontend + 1 QA (частичная загрузка);
- оценка дана в Story Points (SP), ориентир скорости: 20-30 SP за спринт.

### Sprint 1. Основа учета и переназначения (MVP-1)

Цель спринта:
- обеспечить корректную модель связей техники и базовые операции переназначения.

Состав работ:
1. A1-A4: связи ТС, ограничения целостности, миграции, индексы.
2. B1 (частично): сервисы частичного/массового переноса.
3. C1-C2: модальное окно с режимами и зависимыми полями.
4. F1: единый справочник статусов.

Оценка:
- A: 8 SP
- B (частично): 5 SP
- C (частично): 5 SP
- F (частично): 3 SP
- Итого: 21 SP

Зависимости:
- B и C зависят от завершения A (структура связей).
- F1 должен быть завершен до полноценных фильтров и индикации.

Критерии завершения Sprint 1:
1. В БД работают связи «системный блок -> мониторы/диски/ИБП».
2. Доступны сценарии частичного и массового переноса в модальном окне.
3. Статус обязателен для новой/изменяемой единицы техники.

### Sprint 2. Расширение UI и кадровые сценарии (MVP-2)

Цель спринта:
- закрыть ключевые пользовательские сценарии: увольнение, детализация компонентов, статусы в интерфейсе.

Состав работ:
1. B2-B4: сценарий увольнения, аудит, транзакционность.
2. C3-C4: предпросмотр изменений и серверная валидация.
3. D1-D4: отображение нескольких мониторов/дисков и быстрые действия.
4. F2-F4: индикаторы статусов, фильтры, представления по статусам.

Оценка:
- B (остаток): 8 SP
- C (остаток): 5 SP
- D: 8 SP
- F (остаток): 5 SP
- Итого: 26 SP

Зависимости:
- D зависит от финальной модели A.
- F2-F4 зависит от утвержденного справочника F1.
- B2 (увольнение) зависит от готовности B1 и C.

Критерии завершения Sprint 2:
1. Сценарий «увольнение пользователя» завершает передачу техники или перевод на склад.
2. В интерфейсе видно множественные мониторы/диски у системного блока.
3. Доступны списки техники «В эксплуатации», «В ремонте», «На списание».

### Sprint 3. Карточки и обмен данными (Release Candidate)

Цель спринта:
- реализовать карточки пользователя и полный контур XLSX обмена.

Состав работ:
1. E1-E6: карточки, DOCX, реестр карточек, подтверждение подписи, автосброс подписи.
2. G1-G5: выбор столбцов, экспорт XLSX, шаблон, импорт с проверкой и подтверждением, журнал импортов.
3. Регрессионное тестирование и подготовка инструкции администратора.

Оценка:
- E: 10 SP
- G: 11 SP
- Тестирование и инструкция: 4 SP
- Итого: 25 SP

Зависимости:
- E5 зависит от готовых событий изменения локации/закрепления (B).
- G2/G4 зависят от стабильного набора полей и справочников (A, F).

Критерии завершения Sprint 3:
1. Карточка пользователя генерируется в DOCX и учитывает только актуально закрепленную технику.
2. Администратор может отмечать бумажное подписание, а при изменениях отметка автоматически снимается.
3. Работают экспорт и импорт XLSX с протоколом валидации и подтверждением перед записью.

## 10. Сквозные подзадачи (для всех спринтов)

1. Подготовка тест-кейсов на каждый пользовательский сценарий (QA).
2. Контроль прав доступа (администратор/оператор/пользователь) для новых операций.
3. Актуализация документации по мере закрытия задач.
4. Демонстрация бизнес-заказчику в конце каждого спринта с фиксацией замечаний.

## 11. Предложение по старту реализации

Для начала разработки рекомендуется утвердить:
1. кардинальность связи ИБП с системным блоком;
2. формат отображения множественных компонентов в таблице;
3. шаблон бумажной карточки и состав полей DOCX;
4. формат XLSX-шаблона и перечень обязательных полей импорта.

## 12. Структура задач в формате Jira (Epic -> Story -> Sub-task)

### EPIC-1. Связи техники и модель данных
Приоритет: Highest  
Спринт: Sprint 1

Story 1. Реализовать связи ТС в БД  
Definition of Done:
- миграции применяются без ошибок;
- связи и ограничения целостности проверены тестовыми данными;
- добавлены необходимые индексы.

Sub-task:
1. Спроектировать ER-изменения и ограничения.
2. Создать и применить миграции.
3. Добавить индексы на ключевые поля фильтрации.
4. Подготовить SQL-проверки целостности.

Story 2. Обеспечить работу модели в backend-слое  
Definition of Done:
- CRUD-операции корректно обрабатывают связи;
- отсутствуют нарушения ссылочной целостности;
- покрыты базовые сценарии unit/integration тестами.

Sub-task:
1. Обновить модели/репозитории.
2. Обновить сервисы сохранения и обновления.
3. Добавить проверку конфликтов связей.
4. Добавить тесты на создание и изменение связей.

### EPIC-2. Перенос и переназначение техники
Приоритет: Highest  
Спринты: Sprint 1-2

Story 1. Массовый и частичный перенос техники  
Definition of Done:
- доступен перенос комплекта и выбранных единиц;
- операции выполняются в транзакции;
- изменения фиксируются в журнале.

Sub-task:
1. Реализовать сервис массового переноса.
2. Реализовать сервис частичного переноса.
3. Добавить откат при ошибках.
4. Добавить запись аудита по каждой операции.

Story 2. Сценарий увольнения пользователя  
Definition of Done:
- доступна передача техники другим пользователям;
- доступен перевод всей техники на склад;
