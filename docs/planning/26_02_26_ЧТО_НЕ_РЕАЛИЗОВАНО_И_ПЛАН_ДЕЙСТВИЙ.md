## 2. Детальный перечень нереализованного и доработок

### 2.1. Нулевая волна (безопасность) — обязательно

Источник: ПЛАН_РЕАЛИЗАЦИИ.md, раздел «Нулевая волна».

| № | Работа | Где делать | Действия |
|---|--------|-------------|----------|
| 0.1 | Пароли | `ias_uch_vnii/models/entities/Users.php`, `models/forms/LoginForm.php` | В `Users::setPassword()` использовать `Yii::$app->security->generatePasswordHash($password)` (bcrypt). В `LoginForm::validatePassword()` вызывать `$user->validatePassword($this->password)`; убрать логирование пароля из `Yii::debug`. В `Users::validatePassword()` сохранить поддержку старого MD5 только при первом входе с последующим обновлением на bcrypt. |
| 0.2 | Тестовые/опасные экшены | `ias_uch_vnii/controllers/UsersController.php` | Удалить или ограничить доступом (только админ + проверка): `actionResetPassword`, `actionTestPasswords`, `actionIndex2`. Либо вынести в контроллер, отключённый в production. |
| 0.3 | Вложения: проверка прав | `ias_uch_vnii/controllers/TasksController.php` | В `actionDownload` и `actionPreview`: по attachmentId определить заявку; проверить, что текущий пользователь — автор заявки, исполнитель или администратор. При отказе — 403. |
| 0.4 | Вложения: SVG и заголовки | Тот же контроллер | В `actionPreview`: для расширения svg не отдавать с `Content-Disposition: inline` (скачивание или блокировка). Для всех отдач файлов добавить заголовок `X-Content-Type-Options: nosniff`. |
| 0.5 | Get-user-equipment | `TasksController::actionGetUserEquipment($userId)` | Разрешать запрос только если `$userId == Yii::$app->user->id` или текущий пользователь — администратор. Иначе — 403 или пустой массив по политике. |

## 3. Рекомендуемый порядок выполнения (инструкции)

### Шаг 1. Нулевая волна (1–3 дня)

1. Открыть `ias_uch_vnii/models/entities/Users.php`: в методе `setPassword()` заменить сохранение MD5 на `Yii::$app->security->generatePasswordHash($password)`.
2. В `Users::validatePassword()`: оставить сравнение через `security->validatePassword()` для нового формата; при успехе для старого MD5 — один раз обновить запись в БД на новый хеш (bcrypt).
3. В `models/forms/LoginForm.php`: в `validatePassword()` вызывать `$user->validatePassword($this->password)`; удалить любой вывод/логирование пароля в `Yii::debug`.
4. В `UsersController`: удалить или ограничить доступом (например, `if (!Yii::$app->user->can('admin')) throw new ForbiddenHttpException();`) для `actionResetPassword`, `actionTestPasswords`, `actionIndex2`.
5. В `TasksController`: в `actionDownload` и `actionPreview` — по ID вложения найти заявку (через связь task_attachments или по полю tasks.attachments); вызвать проверку доступа (автор/исполнитель/админ); при отказе — `throw new ForbiddenHttpException()`. Для SVG в preview не использовать `Content-Disposition: inline`. Для всех ответов с файлом добавить заголовок `X-Content-Type-Options: nosniff`.
6. В `actionGetUserEquipment($userId)`: в начале экшена проверить `$userId == Yii::$app->user->id || текущий пользователь администратор`; иначе — 403 или пустой массив.

После выполнения: проверить вход под пользователем с паролем в новом формате и при необходимости под старым (миграция хеша).

### Шаг 2. Первая волна (2–4 дня)

1. В `TasksController` добавить метод:
   ```php
   private function canUserAccessTask(Tasks $task): bool
   {
       $user = Yii::$app->user;
       if ($user->isGuest) return false;
       if (/* администратор */) return true;
       if ($task->requester_id == $user->id) return true;
       if ($task->executor_id == $user->id) return true;
       // при необходимости: роль оператор по матрице
       return false;
   }
   ```
2. В начале каждого из экшенов: view, update, delete, changeStatus, assignExecutor, updateComment, deleteAttachment, download, preview — получить заявку по id и вызвать `if (!$this->canUserAccessTask($task)) throw new ForbiddenHttpException();`.
3. В `getUsersList()` и во всех местах, где формируется список пользователей для выбора исполнителя, использовать ключ `id` (или тот, что является первичным ключом в таблице users в текущей схеме).
4. Убедиться, что таблица `audit_events` создана (по scripts/create_ias_vniic.sql) и компонент `AuditLog` вызывается при удалении заявки, удалении вложения, смене пароля и при необходимости при других критичных операциях. Экран журнала аудита с фильтрами — проверить в AuditController.

### Шаг 3. Документация этапа 1 (параллельно или сразу после)

1. Создать или обновить документ «Роли и права доступа» (например, docs/sistema/РОЛИ_И_ПРАВА_ДОСТУПА.md): таблица (роль × операция), отдельно описание роли «оператор».
2. Зафиксировать в документе или в ТЗ режим AG Grid (клиентская/серверная пагинация) и при серверной — формат запроса/ответа.
3. В docs/bd/ОСНОВНОЙ_УЧЕТ_И_БД.md зафиксировать решение по схеме (arm vs equipment) и маппингу полей листа АРМ.
4. Создать или обновить docs/СПЕЦИФИКАЦИЯ_API.md: список эндпоинтов, методы HTTP, параметры, примеры ответов, коды ошибок.

### Шаг 4. Связь заявка–актив и вложения

1. Проверить в формах заявки (create/update): есть ли выбор оборудования (активов) и сохранение в task_equipment. Если нет — добавить поле (множественный выбор) и при сохранении заявки записывать/удалять строки в task_equipment.
2. В карточке актива (view): вывести блок «Связанные заявки» через связь equipment → task_equipment → tasks.
3. Если вложения до сих пор хранятся в tasks.attachments (JSON): создать таблицу task_attachments по целевой схеме; написать миграцию (перенос id из JSON в task_attachments); перевести код на использование связи через task_attachments.

### Шаг 5. Импорт и отчётность

1. Запустить `python3 scripts/load_ou_main.py` с файлом «Основной Учет.xlsx» (или ОУ_тест.xlsx) и проверить, что данные попадают в equipment, locations, users, part_char_values. При ошибках схемы или маппинга — доработать скрипт по docs/import_ou/РЕГЛАМЕНТ_ПАРСИНГА_ОУ_ТЕСТ.md и docs/СТРУКТУРА_ЛИСТА_АРМ_ОСНОВНОЙ_УЧЕТ.md.
2. При необходимости реализовать в приложении экран импорта (только для админа) или консольную команду Yii2, вызывающую ту же логику загрузки с выводом протокола.
3. Универсальный импорт CSV/JSON/XML/XLSX: по ТЗ реализовать загрузку с валидацией и протоколом (в приложении или отдельной утилитой).
4. Контур «ПО и лицензии»: добавить уведомления об истечении лицензий (способ и регламент — по решению заказчика) и при необходимости экспорт в PDF/HTML по перечню отчётов ТЗ.

### Шаг 6. Этапы 4–7

- Этап 4: оформить регламент миграции и контрольные сверки; убедиться, что скрипты создания БД и дампы актуальны.
- Этап 5: составить программу и методику испытаний; провести модульные и интеграционные проверки; зафиксировать результаты в протоколах.
- Этап 6: подготовить руководство пользователя и администратора, регламенты эксплуатации.
- Этап 7: подготовка инфраструктуры, назначение ответственных, начальное наполнение, приёмочные испытания и ввод в эксплуатацию.

## 4. Проверка перед закрытием этапов

- **Нулевая волна:** пароли не в MD5; нет доступа к тестовым экшенам без прав; скачивание/предпросмотр вложений и get-user-equipment только при наличии доступа к заявке/пользователю; для SVG нет inline; заголовок nosniff установлен.
- **Первая волна:** доступ к заявке (просмотр, изменение, вложения) только у автора, исполнителя или администратора; список исполнителей корректен; критические операции попадают в audit_events.
- **Документация:** роль «оператор», режим AG Grid, схема импорта и спецификация API зафиксированы в проектных документах.
- **Функциональность:** связь заявка–актив отображается в форме заявки и в карточке актива; вложения при необходимости нормализованы; импорт из ОУ воспроизводим и с протоколом; при необходимости реализован универсальный импорт и уведомления по лицензиям.
