# Интенты ИИ-помощника ИАС

Документ описывает набор интентов (намерений) помощника, способ их распознавания, параметры и формат ответа. В конце приведены варианты развития с учётом использования LLM.

---

## 1. Общие сведения

- **Распознавание:** выполняется в `app\components\assistant\AssistantIntentParser::parse($message, $currentUserId)` (PHP). Используются ключевые слова и регулярные выражения; текст нормализуется (пробелы, нижний регистр).
- **Обработка:** контроллер `app\controllers\AssistantController::actionQuery()` по полю `intent` вызывает соответствующий метод построения ответа и возвращает JSON с полями `interpretation`, `data`, `link`, `hints`, `helpText` (при справке). Реализация помощника — только на PHP.
- **При неопределённом интенте** (`intent === null`) возвращаются подсказки (`hints`); при включённой локальной LLM (LlmClient) запрос может быть передан в модель для генерации текста подсказки.

## 2. Перечень интентов (текущая реализация)

### 2.1. Справка

| Поле | Значение |
|------|----------|
| **intent** | `help` |
| **Направление** | Справка |
| **Параметры** | — |
| **Триггеры** | Ключевые слова: «справка», «помощь», «как создать заявку», «как создать обращение», «инструкция», «подсказка», «что умеешь», «что можешь» |
| **Ответ** | Текст справки (`helpText`), без таблицы данных. Ссылка не возвращается. |
| **Права** | Все авторизованные |

### 2.2. Мои заявки (где я автор)

| Поле | Значение |
|------|----------|
| **intent** | `my_tasks` |
| **Направление** | Заявки |
| **Параметры** | `TasksSearch[requester_id]` = ID текущего пользователя |
| **Триггеры** | «мои заявки», «мои обращения», «заявки где я автор», «где я автор», «заявки которые я создал», «созданные мной», «мои задачи» |
| **Ответ** | Таблица заявок (id, description, status_name, user_name, executor_name, date, view_url). Ссылка: «Открыть в разделе Заявки» с фильтром по автору. |
| **Права** | Ограничение по правам в TasksSearch (пользователь видит только свои и где исполнитель) |

| **Ответ** | Таблица заявок за период. Ссылка: «Открыть в разделе Заявки» с фильтром по датам. |
| **Права** | По общим правилам заявок |

### 2.5. Заявки по статусу

### 2.8. Техника по ответственному (ФИО)

| Поле | Значение |
|------|----------|
| **intent** | `equipment_by_person` |
| **Направление** | Техника / Пользователи |
| **Параметры** | `responsible_name` — строка поиска по ФИО (часть фамилии/имени). Поиск по Users (ilike full_name), при нескольких совпадениях берётся первый. |
| **Триггеры** | Regex: «(покажи )?технику/техника/оборудование + <текст>», «что закреплено за + <текст>», «техника сотрудника + <текст>», «инвентарь + <текст>» (длина текста ≥ 2) |
| **Ответ** | Таблица техники (id, name, inventory_number, equipment_type, status_name, responsible_name). dataType: equipment. Ссылка: «Открыть в разделе Технические средства» с ArmSearch[responsible_user_id]. При пустом ФИО или ненайденном пользователе — подсказки. |
| **Права** | Обычный пользователь — только своя техника (responsible_user_id = current user); оператор/админ — любая. |

### 2.9. Техника по локации

| Поле | Значение |
|------|----------|
| **intent** | `equipment_by_location` |
| **Направление** | Техника / Локации |
| **Параметры** | Либо `location_query` = `'all'` (сводка по всем локациям), либо `location_name` — строка поиска (название кабинета, тип «кабинет»/«серверная»/«склад»/«лаборатория»). Нормализация падежей в normalizeLocationSearchString. |
| **Триггеры** | «техника по кабинетам», «техника по локациям», «оборудование по кабинетам» → all; «техника в кабинете 203», «оборудование в серверной», «что в кабинете X», «какая техника в кабинете X», «оборудование в комнате X» → location_name |
| **Ответ** | При all — таблица локация + кол-во техники (header/row), summary (total_units, total_locations). При конкретной локации — таблица техники в этой локации. dataType: equipment для списка единиц. Ссылка: «Открыть в разделе Технические средства» (при локации — с ArmSearch[location_id]). |
| **Права** | Все авторизованные (ограничений по локациям нет) |

## 3. Порядок проверки интентов

Парсер проверяет интенты в следующем порядке (первое совпадение возвращается):

1. Пустое сообщение → unknown  
2. help  
3. my_tasks  
4. tasks_executor  
5. tasks_period (detectPeriod)  
6. tasks_status (detectStatus)  
7. statistics  
8. tasks_all  
9. list_locations  
10. list_users  
11. equipment_by_location (detectEquipmentByLocation)  
12. equipment_by_person (два regex-шаблона)  
13. unknown

## 4. Расширение интентов и использование LLM в будущем

Ниже перечислены возможные направления развития. Реализация зависит от приоритетов и готовности инфраструктуры (в т.ч. стабильности локальной или облачной модели).

### 4.1. Новые интенты (без LLM)

- **Поиск техники по инвентарному номеру** — запросы вида «техника по инвентарному номеру X», «найди оборудование № X». Параметр: `inventory_number`. Ответ: одна или несколько записей Equipment с ссылкой на карточку.
- **Заявки по автору (ФИО)** — «заявки Иванова», «заявки от Петровой». Параметр: поиск пользователя по ФИО, затем `requester_id`. Только для оператора/админа или с проверкой прав.
- **Заявки по исполнителю (ФИО)** — «заявки на исполнении у Сидорова». Аналогично, фильтр `executor_id`.
- **Комбинированные фильтры заявок** — «открытые заявки за месяц», «мои заявки в работе». Парсер может возвращать несколько параметров TasksSearch (date_from/date_to + status_id, requester_id + status_id). Требует расширения шаблонов или LLM-классификации.
- **Краткая сводка по технике** — «сколько всего техники», «сколько единиц в кабинете 203». Отдельный интент или вариант equipment_by_location с ответом только summary.

### 4.2. LLM как классификатор интента

- **Идея:** при `intent === null` перед показом подсказок один раз вызвать LLM с промптом: «По запросу пользователя верни JSON: {"intent": "<имя интента>", "params": {...}}. Доступные интенты: my_tasks, tasks_period, tasks_status, ...». По ответу парсить JSON и выполнить соответствующий интент.
- **Плюсы:** распознавание формулировок, не покрытых шаблонами.  
- **Минусы:** слабая модель может вернуть невалидный JSON или неверный интент; задержка ответа; необходимо ограничить список интентов и форматов params в промпте.
- **Рекомендация:** опциональный режим (настройка в params), fallback на подсказки при ошибке парсинга или при недоверии к ответу.

### 4.3. LLM с контекстом данных (RAG-подход)

- **Идея:** передавать в модель не только системный промт с направлениями, но и краткий контекст из БД: например, список ФИО ответственных, названия локаций, последние N заявок пользователя. Модель формирует ответ или уточняющий вопрос с опорой на эти данные.
- **Плюсы:** более релевантные ответы, возможность уточнений («Имеете в виду кабинет 203 или 205?»).  
- **Минусы:** объём контекста ограничен размером окна модели; риск утечки данных при облачной модели; сложнее валидировать ответ.
- **Реализация:** отдельный слой подготовки контекста (топ пользователей, топ локаций, сводка по текущему пользователю), подстановка в системное или пользовательское сообщение.

### 4.4. Диалоговая история (мульти-turn)

- **Идея:** хранить в сессии (или в БД) последние пары «запрос — ответ» и при следующем запросе передавать их в LLM как историю диалога. Это позволит обрабатывать уточнения: «Покажи технику» → «Техника какого ответственного?» → «Печерского».
- **Плюсы:** естественный диалог, меньше повторных вводов.  
- **Минусы:** рост размера запроса к LLM; необходимо ограничить длину истории (например, последние 5–10 реплик); при слабой модели возможны «забывания» контекста.
- **Реализация:** массив сообщений в `Yii::$app->session['assistant_history']`, передача в LlmClient в формате messages ([role => user/assistant, content => ...]). Опционально использовать историю только при `intent === null`.

### 4.5. Генерация подсказок и формулировок

- **Идея:** использовать LLM для генерации текста интерпретации (например, «Показаны заявки за последний месяц — всего 12») или персонализированных подсказок («Вы можете запросить заявки за период или технику по кабинету»).
- **Плюсы:** более живой язык ответов.  
- **Минусы:** непредсказуемость формулировок; необходимо задать жёсткие границы (не выдумывать числа, не менять смысл).

### 4.6. Облачная модель и политики

- **Идея:** поддержка облачного OpenAI-совместимого API (OpenAI, Yandex GPT и т.п.) в дополнение к локальной LM Studio. Разделение настроек: base_url, api_key, модель; политика «только локально» для конфиденциальных данных.
- **Учёт:** при передаче контекста (RAG, история) в облако не включать персональные данные или только в обезличенном виде, в соответствии с регламентом безопасности.

### 4.7. Извлечение сущностей (NER) через LLM

- **Идея:** для интентов с параметрами (ФИО, номер кабинета, дата) вызывать модель с просьбой извлечь сущности из запроса в формате JSON, например: `{"responsible_name": "Печерский", "location": null}`. Бэкенд подставляет их в params и выполняет уже известный интент.
- **Плюсы:** распознавание формулировок вроде «покажи что закреплено за Печерским в кабинете 203».  
- **Минусы:** зависимость от качества JSON и согласованности с допустимыми значениями в БД; нужна валидация и fallback на шаблоны.

### 4.8. Приоритеты внедрения (рекомендуемый порядок)

1. Расширение шаблонов и новых интентов без LLM (поиск по инв. номеру, заявки по ФИО при правах) — быстрый выигрыш.  
2. Опциональная история диалога в сессии и передача последнего обмена в LLM при неопределённом интенте — улучшение UX без смены архитектуры.  
3. LLM как классификатор — только после стабилизации набора интентов и с строгой схемой ответа и fallback.  
4. RAG и извлечение сущностей — при необходимости более «умного» поведения и при наличии ресурсов на поддержку промптов и валидации.
